# 에이전트 평가

정답 있는 명령 30개로 "에이전트가 도구를 맞게 고르고 인자를 맞게 채우는지"를, 이어지는 대화 · 스스로 고치기 9개로 "앞 대화를 기억하고 오류를 스스로 수습하는지"를 잰다.

```powershell
cd backend
compose_venv\Scripts\python -m eval.run                                  # .env의 모델 (지금 gpt-6-luna)
compose_venv\Scripts\python -m eval.run --models gpt-6-luna,gpt-5.4-mini # 모델 비교
```

- 명령과 정답: [backend/eval/cases.py](../backend/eval/cases.py) · 채점: [backend/eval/spec.py](../backend/eval/spec.py)
- 결과 원본(명령마다 부른 도구 · 인자 · 답 · 시간 · 토큰): `backend/eval/results/`
- 실제 API를 부르므로 비용이 든다. 명령 하나에 입력 토큰 약 5,500~5,900개(대부분 도구 설명과 규칙), 출력 70~80개.

## 명령 30개

| 분야 | 개수 | 예 |
| --- | --- | --- |
| 조옮김 · 옥타브 | 7 | "베이스 2키 올려줘", "2마디부터 4마디까지 베이스 한 옥타브 올려줘" |
| 퀀타이즈 | 5 | "코드 박자 정리해줘, 너무 딱딱하진 않게", "베이스 박자를 50%만 당겨줘" |
| 세기 | 6 | "하이햇 좀 약하게", "9마디부터 패드 약하게", "베이스 볼륨 20 줄여줘" |
| 스윙 | 4 | "하이햇에 살짝 스윙 넣어줘", "16분음표 스윙 60%로" |
| 여러 도구 | 3 | "하이햇 좀 약하게 하고 살짝 스윙 넣어줘" |
| 편집하면 안 됨 | 5 | "좀 더 좋게 해줘"(막연함), "드럼 2키 올려줘"(드럼은 조옮김 대상 아님), "스트링 트랙 올려줘"(없는 트랙) |

## 채점

- 실제로 음을 바꾼 편집만 본다 (정보 조회 · 실패한 호출 · 바뀐 음 0개는 제외). **시키지 않은 편집을 더 하면 오답.**
- 정도를 말하는 명령은 범위로 채점: "좀 약하게" = 0.5~0.85배 또는 −8~−40, "살짝 스윙" = 53~60%, "너무 딱딱하지 않게" = 강도 0.5~0.85
- 같은 결과를 내는 다른 방법도 정답: 한 옥타브 = `shift_octave ±1` 또는 `transpose ±12`, 세기 = 곱하기 또는 더하기
- 하이햇은 42(닫힘) · 44(페달) · 46(열림) 안에서 고르되 42는 꼭 포함
- 정답 30개가 실제 도구로 만들 수 있는 답인지도 테스트로 확인한다 (`tests/test_eval.py`): 정답 호출을 그대로 실행하면 음이 바뀌고 정답으로 채점돼야 한다

3회차 기준: 응답 시간 중앙값 gpt-6-luna 3.1초 · gpt-5.4-mini 2.2초, LLM 호출 평균 약 2회(도구 한 번 + 답).

### 배운 것

- **1회차의 3개 실패는 모델이 아니라 우리 코드 문제였다.** 일부 모델은 도구를 쓰려면 `reasoning_effort='none'`이 필요해서 오류가 나면 자동으로 바꿔 다시 부르게 해 두었는데, 명령 4개를 동시에 보내면 먼저 실패한 요청이 설정을 바꿔 놓는 바람에 나머지는 "이미 바뀌었다"고 보고 재시도 없이 실패했다. 이번 요청이 실제로 보낸 값으로 판단하도록 고치고 테스트로 고정했다. 서버에 여러 사람이 동시에 요청할 때도 같은 문제가 날 뻔했다.
- **"스트링 트랙 올려줘"(없는 트랙)**: 처음엔 Pad를 "스트링 역할"이라 짐작해 편집했다. 규칙을 넣은 뒤 2회차엔 맞았지만 3회차에 다시 틀렸다 → 아직 불안정한 명령.
- **"베이스 박자를 50%만 당겨줘"**: gpt-5.4-mini가 스윙 50%(= 변화 없음)로 읽었다. "박자를 당긴다"는 격자 쪽으로 당기는 것(퀀타이즈)이라는 용어 규칙을 넣고 맞았다.
- **같은 모델도 회차마다 결과가 달라진다** (gpt-6-luna 30 → 29). 한 번 돌린 숫자는 믿기 어려워서, 모델마다 3번 이상 돌려 평균 · 범위로 보고하는 게 다음 할 일이다.
- 정확도는 두 모델이 비슷하고 gpt-5.4-mini가 1초쯤 빠르다. 하지만 **비용은 gpt-6-luna가 훨씬 싸다** (아래 표). 그래서 기본 모델은 gpt-6-luna로 둔다.

## 이어지는 대화 · 스스로 고치기 (39개로 확장)

한 명령만 보는 30개로는 에이전트다운 부분(맥락 기억 · 오류 수습)을 잴 수 없어서 9개를 더했다 ([backend/eval/conversations.py](../backend/eval/conversations.py)). 실제 서버와 같은 코드(`app/agent/session.py`)로 여러 턴을 돌리고, 정답으로 가는 길이 여러 개라 **마지막 상태**로 채점한다.

| | 예 | 확인하는 것 |
| --- | --- | --- |
| 이어지는 대화 6개 | "베이스 2키 올려줘" → 적용 → "한 키 더", "패드 한 옥타브 올려줘" → "아니 내려줘", "하이햇 좀 약하게" → 취소 → "그럼 스네어를 20만큼 세게" | 앞 대화 · 적용 · 취소를 기억하는지 |
| 스스로 고치기 3개 | "베이스 30반음 올려줘"(한 번에 최대 24), "리드를 4옥타브 올려줘"(MIDI 범위 밖), "20마디부터 베이스 약하게"(곡은 16마디) | 도구 오류를 보고 나눠 하거나, 안 되면 바꾸지 않고 설명하는지 |

### 처음 돌렸을 때 드러난 약점 → 고친 것

| 명령 | 처음 | 원인 | 고친 것 |
| --- | --- | --- | --- |
| "패드 한 옥타브 올려줘 → 아니 내려줘" | 0/3 (+1 위에 −1 → 원래대로) | 미리보기에 계속 쌓기만 하고 "버리고 다시"가 없었다 | `start_over` 도구: 이번 명령의 편집과 미리보기를 버리고 현재 버전에서 다시 |
| "베이스 30반음 올려줘" | 0/3 (24만 올리고 끝) | 오류 메시지가 "나눠서 하면 된다"를 알려 주지 않았다 | 범위 오류에 "나눠서 같은 결과를 낼 수 있으면 나눠 부르고, 아니면 바꾸지 말고 알려 줘" |
| "리드를 4옥타브 올려줘" | 0/3 (말없이 3옥타브로 바꿈) | 다른 값으로 바꿔 넣지 말라는 규칙이 없었고, 나눠 하다 중간에 실패하면 반쯤 바뀐 채로 남았다 | "다른 값으로 바꾸지 말고 되묻기" 규칙, 2옥타브 이상은 음역 + 반음이 127을 넘는지 먼저 확인, 중간에 실패하면 `start_over`로 되돌리기 |

규칙을 하나 넣을 때마다 다른 데가 흔들렸다. "옮기기 전에 음역 확인" 규칙을 모든 조옮김에 걸었더니 gpt-5.4-mini가 겁을 먹어 "건반 5반음"에서 정보만 보고 멈추고, 드럼 소리 고르기(pitches)를 빼먹어 37.3 → 32.7로 떨어졌다. 확인은 2옥타브 이상일 때만, 드럼 소리 하나를 말하면 pitches를 꼭 넣으라는 문장을 강조해 되돌렸다. **작은 모델일수록 규칙 문장 하나에 크게 흔들린다.**

채점 수정: "전부 16분음표로 퀀타이즈"를 멜로디 트랙과 드럼으로 나눠 두 번 부른 것도 결과가 같아 정답으로 추가했다(그 전에는 오답 처리). 저장된 결과를 API 호출 없이 다시 채점했다.

## 템포 도구 추가 (42개)

"템포 100으로 바꿔줘"가 안 됐다 — 음표를 고치는 도구만 있었기 때문. `set_tempo`(set · offset · scale, 20~300 BPM)를 추가했다. 음표는 박 단위로 저장해서 템포만 바꾸면 마디 위치는 그대로다. 음표가 하나도 안 바뀌어도 미리보기 · 버전이 생기도록 "바뀐 음 수"만 보던 판정을 "곡 설정이 바뀜(changed_settings)"까지 넓혔다.

## 악기 바꾸기 (48개)

"악기를 바꿀 수 있나?"라는 요청으로 `set_instrument`(트랙 · General MIDI 번호 0~127)를 추가했다. 음은 그대로고 악기 번호만 바뀌며, 내보낸 MIDI에도 그 번호가 들어간다. 드럼 트랙은 음 번호가 곧 드럼 소리라 건너뛴다. 프롬프트에 자주 쓰는 악기 번호 약 50개를 한국어 이름으로 넣고, "신스로"처럼 종류만 말하면 트랙 역할에 맞춰 고르게 했다.

### 입력 토큰 줄이기 (v0.2 5단계, Claude Haiku 5.5)

호출 한 번에 들어가는 것을 토큰 세기 API로 쟀다: 규칙(시스템 프롬프트) 약 6,500 + 도구 설명 11,512. 도구 설명의 대부분은 설명 글이 아니라 pydantic이 만든 인자 스키마였다.

- **스키마 군더더기 덜기** (`compact_schema`): `title`(인자 이름과 같음), "없어도 됨"을 나타내는 `anyOf [X, null]` · `default: null`, 같은 타입 두 개짜리 tuple의 `prefixItems` → 11,512 → 9,077. 뜻은 같고 검사는 서버의 pydantic이 그대로 한다 (LLM이 null을 보내도 받음).
- **고르기 인자 설명 줄이기**: `track_ids` · `bars` · `pitches` · `beats`가 도구 12개에 똑같이 붙어 도구마다 약 380토큰, 합쳐서 도구 설명의 절반이었다. 설명을 한 줄로 줄이고(쓰임은 규칙에 이미 있음) → 8,159 (−29%).

## 화성 분석 엔진 · LLM 단독 vs LLM + 엔진

v0.2의 원칙("화성은 코드가 계산하고 LLM은 설명만")이 맞는지 확인하는 평가. 에이전트 평가와 따로 돌린다.

```powershell

```

- **생성한 곡**: 정답을 아는 진행(장조 4 · 단조 4)을 12개 조 × 보이싱 6가지(블록 · 자리바꿈 · 근음 없는 건반 · 펼침화음 · 위에 멜로디 · 반 마디씩)로 만든 576곡. 정답이 생성기에서 나와서 넓고 흔들리지 않는다. 엔진을 고칠 때는 이쪽만 보며 고쳤다(개발용).

- 조성 점수: 정답 수와 MIREX 방식 점수(정답 1 · 5도 관계 0.5 · 나란한조 0.3 · 같은 으뜸음조 0.2).
- 코드 점수: 박마다 근음 · 3화음 계열 · 7화음 계열(maj9 → maj7, 13 → 7) · 이름 그대로. 이름은 달라도 음이 똑같은 것(Am7/C = C6, Bø7/D = Dm6, Csus4/F = Fsus2)은 음만 보고는 가릴 수 없어서 "같은 구성음"으로 따로 센다.

- **펼침화음을 멜로디로 봄**: 겹치는 음이 없는 트랙은 모두 멜로디로 보고 비중을 절반으로, 덧붙인 음은 빼고 읽었다 → C7 아르페지오가 C로. 멜로디 = 대부분 2도로 움직이거나, 뛰더라도 리듬이 들쭉날쭉한 것. 3 · 4도로 뛰며 같은 리듬을 되풀이하면 펼침화음(화음 트랙).
- **길게 누른 베이스가 기준이 됨**: "울린 음"을 구간에서 가장 오래 울린 음과 비교해서, 한 번 짚고 지나간 7음이 빠졌다 → 화음 트랙 안에서 그 트랙 소리의 10% 이상이면 울린 음.
- **Cmaj7/E를 Em으로**: 베이스 가산점이 근음 위 b6(C)의 감점보다 커서 → b6 감점을 근음 위 b2만큼.
- **밀집 화음의 맨 아래 음을 베이스로 봄** (5단계 뒤): 베이스 트랙 없이 건반만 친 C E A에서 맨 아래 C에 베이스 가산점을 줘 C6으로 읽었다(Am/C ×120, Am7/C ×72) → 맨 아래 음 바로 위 5도 안쪽에 다른 음이 붙어 있으면 가산점 없이 근음을 고른다(슬래시 표기는 그대로). 따로 낮게 친 베이스는 위 음과 멀어서 그대로다.
- **반 마디 코드 바뀜을 합쳐 읽음**: Dm9 → G9를 한 마디로 보면 D F A C E G B라 Dm11 하나로 점수가 높게 나와 나누지 않았다 → 반 마디에 베이스를 새 근음으로 새로 치면 나눈다. 처음엔 "반쪽 베이스가 다르면"만 봤더니 lofi_groove(건반은 Fmaj9를 누른 채 베이스가 쉼)에서 맨 아래 건반 음 A를 베이스로 봐 Fmaj9 | Am7로 나눴다 → 그 박에 새로 친 음인지까지 본다.
- 남은 약점: 자리바꿈 sus4 → sus2 · m7b5 → m6(같은 구성음), 반 마디씩 바뀌는 sus4 → 7, 펼침화음의 9음 빠짐. 샘플팩 37곡 중 5곡의 코드 읽기가 바뀌었는데(조성은 그대로) 정답이 없어 맞는지는 들어 봐야 안다.

조성은 생성한 곡 460/576 → 498/576 (펼침화음을 제대로 읽으면서 같이 좋아짐) → 534/576 (종지를 더해서) → 570/576 (자리바꿈 · 반 마디를 고쳐서, ii 루프 66/72 · i–VI–III–VII의 나란한조 오답 12개도 사라짐). 진행별로 보면 `ii9–V9–Imaj9–VI7`(Dm9–G9–Cmaj9–A7 루프)이 6/72로 크게 틀렸다 — 루프 첫 코드를 으뜸화음으로 보는 가산점 때문에 D minor로 읽었다. 가산점은 샘플팩에서 정한 값이라 줄이지 않고, 조성을 알려 주는 다른 근거인 종지를 더했다: 코드가 바뀐 자리 중 **버금딸림(ii · IV, 단조는 iiø · iv · VI) → V7 → I**로 끝나는 비율만큼 점수를 준다 (가중치 1.0 — 생성 곡에서 0.5 → 533, 1.0부터 534로 그대로). 두 가지를 일부러 세지 않는다. 7음 없는 V → I(B → E는 B major의 I → IV로도 읽힌다, B7의 3온음 D#–A는 E 조에만 있다)와 앞이 버금딸림이 아닌 V7 → I(루프를 되풀이하면 생기는 A7 → Dm9 — 앞이 Cmaj9라 D minor의 종지 진행이 아니고 C major의 V7/ii → ii)다. → 6/72 → 42/72. 남은 30곡은 조성이 아니라 코드를 잘못 읽은 경우다 (반 마디씩: Dm9 · G9가 한 코드로 합쳐짐, 자리바꿈: Dm9/F → Fmaj7, 펼침화음 일부: 3화음만). 샘플팩은 25/37 그대로. 처음엔 7음 없는 V → I도 셌는데 샘플팩에서 Moments(G#m–Emaj7–B–Emaj7, G# minor)가 E major로 바뀌어 24/37이 됐다 — 이걸 보고 7음 규칙을 생각했으니 샘플팩을 한 번 들여다본 셈이다. 다만 생성 곡에서는 두 규칙이 똑같이 533이라 이론에 맞는 쪽을 골랐다. 처음 넣었던 `i7–iv7–VII7–IIImaj7`(Am7–Dm7–G7–Cmaj7)은 0/72였는데 엔진이 C major로 읽은 것 — C major의 vi–ii–V–I로 듣는 게 자연스러워 정답이 모호해서 `i–VII–VI–V7`(안달루시아 종지)로 바꿨다.

샘플팩 37곡 조성: 정답 25/37 · 후보 3개 안 33/37 · MIREX 0.75 (위 개선 전후 같음 — 펼침화음 · 자리바꿈 고친 것이 조성에는 영향이 없었다).

### LLM 단독 vs LLM + 엔진 (Claude Haiku 5.5, 3회 실행)

같은 곡을 세 가지로 읽는다. LLM에게는 음 목록(트랙 · 마디별 "음이름@박/길이")을 주고 조성 · 마디별 코드를 JSON으로 답하게 했다. "LLM + 엔진"은 같은 음 목록에 엔진 결과를 덧붙이고 "엔진도 틀릴 수 있다, 음을 보고 최종 판단"이라고 했다. LLM은 매번 답이 달라서 3번 돌렸다 (값은 1회 / 2회 / 3회, 엔진은 매번 같다).

| | 생성한 곡 72곡 조성 | 코드 7화음 | 샘플팩 37곡 조성 | 샘플팩 MIREX | 입력+출력 토큰 (곡당) |
| --- | --- | --- | --- | --- | --- |
| **엔진만** | **64/72** | 99% | **25/37** | **0.75** | 0 |
| LLM만 | 58 / 56 / 58 | 95 / 96 / 96% | 15 / 19 / 18 | 0.53 / 0.63 / 0.60 | 2,000~3,300 |
| LLM + 엔진 | 63 / 59 / 62 | 98 / 100 / 100% | 23 / 21 / 22 | 0.71 / 0.65 / 0.69 | 1,900~3,500 |

코드 근음은 세 방식 모두 99~100%라 표에서 뺐다.

이 비교는 종지 · 자리바꿈 · 반 마디를 고치기 전 엔진으로 쟀다. 지금 엔진만은 생성 곡 72곡 조성 71/72 · MIREX 0.99 (샘플팩은 그대로 25/37).

- 엔진이 조성을 가장 잘 맞힌다. LLM에게 음을 보고 직접 판단하게 하면 실제 루프에서 조성이 크게 틀린다(평균 17/37).
- LLM에게 엔진 결과를 주고 "고쳐도 된다"고 하면 3회 모두 엔진보다 나빴다. 샘플팩에서 엔진과 다르게 답한 경우를 모으면 4번 고치고 13번 망쳤다 (나머지 2번은 틀린 답을 다른 틀린 답으로). 코드 7화음만은 LLM이 엔진의 작은 실수를 고쳐 조금 나았다.
- → 에이전트가 `analyze_harmony` 결과를 그대로 전하게 한 지금 설계가 맞다.
- LLM은 음 목록을 따지느라 생각이 길어져, 에이전트 기본 출력 한도(2,048토큰)로는 답을 쓰기 전에 끊긴 곡이 있었다(평가에서는 8,000으로 올림). 화성을 LLM에게 맡기면 느리고 비싸기도 하다.
- **처음 실행에서 LLM만 37/37이 나왔는데 정답이 새어 나간 것이었다**: 샘플팩 MIDI의 트랙 이름이 파일 이름("Cymatics - Alarma MIDI - E Min")이라 음 목록 머리에 키가 적혀 있었다. 트랙 이름을 "트랙 1"로 가리고 다시 돌린 결과가 위 표다.

| | 정답 | 응답 시간 중앙값 | 입력 토큰 평균 (그중 캐시) | 출력 토큰 평균 |

| --- | --- | --- | --- |
| 샘플 곡 4개 × 스타일 (408박) | 71% | 98% | **98%** |

## 엔진 개선: 텐션 더하기 · 섞인 선율 · 같은 음 다른 이름 (다시 읽기)
